# audit

Скилл для аудита кода: **корректность на неожиданных входах, расхождение
документации с кодом, стоимость по замеру, спорные решения**. Объект — то, что
уже написано и работает: инструмент, скрипт, дерево конфигурации, набор
документов. Находки складываются в один файл `review-YYYY-MM-DD-<object>.md` в
корне проекта.

Чем это **не** является: ни проверкой на уязвимости, ни разбором стиля, ни
рецензией на изменение в истории git. Четыре вопроса, в таком порядке:

1. **Работает ли оно на том, чего автор не ждал?**
   Автор проверял инструмент на тех входах, что держал в голове, — на них всё
   в порядке. Аудит подсовывает другие: ключ, записанный в JSON, а не через
   `=`; пароль со знаком `@` в середине; значение, разорванное переносом
   строки; файл в десять раз больше обычного. И смотрит, что вышло: ответ
   остался верным — или стал неверным, а инструмент об этом промолчал.

2. **Совпадает ли документация с кодом?**
   README обещает, что метка `Authorization: Bearer` распознаётся. В коде такой
   метки нет, и она не срабатывает. Это хуже, чем если бы README молчал: человек
   прочитал, поверил и решил дальше не проверять. Аудит читает документацию и
   проверяет каждое её обещание командой.

3. **Сколько это стоит и с какого размера перестаёт работать?**
   Не «можно быстрее», а секунды и байты, напечатанные командой. Настоящий
   случай: маскировщик тратил 5,6 секунды на мегабайт, а хук, который его
   зовёт, система убивает через 10 секунд. Значит всё, что длиннее двух
   мегабайт, доезжало до читателя незамаскированным. Цена сама по себе —
   замечание; цена, за порогом которой работа не делается, — дефект.

4. **Какие решения стоит обсудить?**
   Код делает то, что задумано, — вопрос к самому замыслу. Например: читать
   секретный файл разрешено пяти командам из списка, а `sort .env` в список не
   попал и читает свободно. Это не дефект, это выбор с ценой. Аудит называет
   цену, решает автор.

За каждой находкой стоит команда, которая её воспроизводит, запущенная на
сломанном входе. Находка без такой команды — догадка, а догадки дёшево писать и
дорого читать.

Скилл ничего не чинит. Рецензировать и править — разные работы: проход, взявшийся
за первую находку, перестаёт искать остальные и до третьей уже не доходит.

```
ты:     /audit bin/mytool
скилл:  Using audit on bin/mytool — findings go to review-2026-09-18-mytool.md
        … baseline, пробы, воспроизведения …
        A: 7, B: 3, C: 4, D: 4 open questions. Nothing was fixed.
```

## Когда запускают audit

Запускаешь ты, руками, когда решил. Скилл не следит за репозиторием, не ходит по
расписанию и ни о чём не напоминает. Поводы, по которым его обычно и зовут:

- **берёшь в работу чужой или свой давний инструмент** и не знаешь, чему в нём
  верить;
- **собираешься менять кусок**, который не трогали полгода;
- **инструмент начал вести себя странно**, а коммитов не было;
- **вокруг что-то поменялось** — версия рантайма, формат входных данных,
  соседний сервис, — и непонятно, пережил ли он это;
- **отдаёшь инструмент другим**: публикуешь, передаёшь коллеге, ставишь в
  общий доступ.

Общее у всех пяти: изменений нет, а вопросы есть. Рецензент изменений смотрит,
что сломала правка; здесь правок не было. Код лежал без движения, а вокруг
менялись версии библиотек, формат входа, соседние сервисы, лимиты хоста. Долг
накопился, коммитов нет, смотреть рецензенту нечего. Увидеть это можно одним
способом: прогнать через код сегодняшние входы.

| Что на входе | Чем смотреть |
|---|---|
| pull request, ветка под слияние, изменение в истории git | то, чем в твоей оболочке рецензируют изменения |
| инструмент, скрипт, дерево конфигурации, набор документов на диске | скилл `audit` |

**`audit` работает в одной сессии и не запускает ни одного субагента.**
Рецензенты изменений обычно раскладывают работу на параллельных агентов; здесь
этого нет, потому что каждый запуск грузит контекст с нуля. Если объект слишком
велик для одной сессии, скилл берёт его часть и в первой же строке говорит,
какую.

## Что даёт проход

Один файл в Markdown, разделы названы по последствиям, а не по темам:

| Раздел | Вопрос |
|---|---|
| **A. Дефекты** | что сломано и как это увидеть |
| **B. Документация** | README обещает одно, код делает другое |
| **C. Стоимость** | сколько потребляет времени и памяти — по числам из команды, не на глаз |
| **D. Решения** | что трогать не надо, а что спорно — предложения автору, не задания |
| **Что дефектом НЕ является** | проверили, всё в порядке — чтобы следующий не проверял заново |
| **Готово, когда** | команды приёмки и какой код возврата ждать от каждой |

Каждый дефект в разделе A описан одинаково, пятью строчками:

- **что сломано** — одной фразой, без разбора причин;
- **команда**, которой это видно, и её настоящий вывод;
- **насколько плохо**: соврал и промолчал, упал и сказал об этом, или испортил
  данные. Первое хуже всех — раз никто не заметил, никто и не пойдёт проверять;
- **что править** — все файлы, которые меняются вместе: порт на другом языке,
  вторая копия того же списка, тест;
- **чем закрыть** — тест, который падает до правки и проходит после.

Сверх находок в файле есть ещё два списка, и без них по нему нельзя работать.

**Инварианты** — то, что правка ломать не имеет права, выписанное из слов
самого проекта: «хук падает в открытую сторону», «политика у обоих портов
одна». Без этого списка правка, закрывающая дыру ценой отказа работать,
выглядит успехом.

**Порядок правок** — какие пункты трогают один и тот же код и делаются вместе,
какой идёт первым и чьи воспроизведения перезапустить после него. Там же
сказано, что остаётся сломанным, пока очередь не дошла: худшая находка обычно
уезжает в конец, потому что иначе остальные правки пришлось бы переносить в
переписанный код.

## Файл — аудит, по которому другая сессия принимает решения

Это не памятка и не отчёт для чтения. Это вход для следующего шага: другая LLM
или новая сессия читает файл и решает по нему, что менять — в коде, в структуре
каталогов, в конфигурации. Проход и правка намеренно делаются разными сессиями,
а файл переносит между ними всё, что нужно для решения. Отдай его другому
ассистенту или этому же в новой сессии:

```
Пройди по review-2026-09-18-mytool.md. Каждый пункт сначала воспроизведи, потом
чини, в том порядке, который задан в файле, и в конце прогони приёмочные команды.
```

Больше передавать ничего не нужно. В каждом пункте лежат четыре вещи: команда,
которая воспроизводит дефект; правка, названная изменением, а не намерением;
файлы, которые меняются вместе; тест, который его закрывает. В файле целиком —
инварианты, порядок пунктов и приёмочные команды с кодами возврата. Контекст
сессии-рецензента тому, кто чинит, не нужен.

Это разделение и есть замысел, а не ограничение. Сессия, которая читала код,
уже верит собственному прочтению; сессия, у которой есть только файл, обязана
воспроизвести каждое утверждение, прежде чем действовать, — ровно это файл и
требует во второй своей строке.

## Правила, которым проход подчиняется сам

- **Сначала воспроизвести, потом утверждать.** Нет команды — нет находки.
- **Запускать на сломанном входе.** Проверка, ни разу не запущенная против
  поломки, которую описывает, не проверена.
- **Цитата из документации — это гипотеза.** Если тяжесть находки держится на
  поведении хоста или среды выполнения, это поведение показывают на этой машине,
  либо
  пункт помечают непроверенным.
- **Вердикт читать по коду возврата.** Сессия работает внутри хуков и обёрток,
  переписывающих вывод; когда объект той же природы, экран не доказывает ничего.
- **Песочница из `mktemp -d`, ничего не удалять.** Каждая итерация чиста,
  потому что новая, — и ни одному пробному скрипту не нужен `rm`.
- **Не выходить за пределы проекта.** Соседний проект на этой машине не
  свидетельствует об этом.
- **Один объект за проход.** Больше примерно 600 строк — объект режут на
  сегменты и берут один. Сегмент — часть, которую можно проверить саму по себе:
  у неё свои входы и своя проверка. Обычно они в проекте уже намечены:
  основная реализация `bin/tool` и её порт `bin/tool.ps1`; библиотека
  `lib/parse.py` и команда, которая её зовёт; одна подкоманда CLI со своими
  флагами; одна подсистема дерева конфигурации. Причина в том, что проход
  укладывается в одну сессию, а её бюджет делится между двумя работами:
  прочитать код и прогнать через него сломанные входы. На пятистах строках
  хватает на обе; на полутора тысячах почти всё уходит на чтение, и пункты
  выходят без воспроизведения — «выглядит рискованно» вместо команды, которая
  это показывает. Порт получает отдельный проход, и тот начинается со сверки:
  одни и те же входы через обе реализации, список расхождений.

## Установка

```bash
git clone <этот репозиторий> audit && cd audit
./install.sh                 # во все найденные: Claude Code, Opencode, Codex
./install.sh --dry-run       # показать, что произойдёт, ничего не писать
./install.sh --skills-dir D  # поставить в D вместо автоопределения
```

Windows: `.\install.ps1`, флаги те же.

Скилл — это три файла Markdown. Ни бинаря, ни записи в `PATH`, за пределы
`$HOME` ничего не пишется. Повторный запуск меняет только изменившееся; файл,
который перезаписывают, копируется в `.bak`, только если такого содержимого нет
в этом репозитории, — правка руками единственное, чего git не вернёт.

Удаление: удалить каталог `<skills-dir>/audit`.

## Что где лежит

```
skills/audit/SKILL.md              сам проход — что делать и в каком порядке
skills/audit/references/
    template.md                    скелет файла ревью, по слотам
    domains.md                     формы, которые пропускают чаще всего, по доменам
install.sh / install.ps1           копирование в каталоги скиллов ассистентов
release.sh                         версия ↔ журнал ↔ тег ↔ HEAD ↔ копии
CHANGELOG.md                       что изменилось в каждом выпуске
```

Обе страницы `references/` грузятся **по надобности**: `template.md` — когда
файл уже пишут, `domains.md` — только если объект одного из описанных там родов.
Обычный проход не платит ни за одну.

## Выпуск

```bash
./release.sh check     # версия ↔ журнал ↔ тег ↔ HEAD ↔ установленные копии
./release.sh tag       # создать тег, в него уезжает секция журнала
```

`check` сверяет каждую установленную копию с источником **пофайлово**, причём
список файлов спрашивает у источника, а не берёт из написанного руками перечня.

## Как присылать правки

Сообщения коммитов пишутся по-английски, вместе с телом. История — единственное
место, где остаётся причина изменения, а кто читает код, прочитает и сообщение.
Если сообщение цитирует русский текст — переименованный заголовок, заменённое
слово, — цитата остаётся: там русский и есть предмет.

Сама документация двуязычная и такой остаётся: `README.md` и `README.RU.md`
правятся парой.
